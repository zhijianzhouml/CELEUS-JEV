02 / EVERY NUMBER

Evaluation summary

CELEUS ran three times with different random seeds, always to the same ±2-point precision. Questions and cost are compared with asking Jev every case in the full pool; the accuracy interval is from run 1, the pre-declared main result.

Four benchmarks
Click a benchmark for its source revision, filtering, stopping rule and accounting. Means use only complete sets of runs that all reached the precision target. Full pool = every eligible case; full-pool cost = pool size × average API cost per question in a uniform random sample of the pool (the full pool was not actually run). Cost per run = API usage of every answer a run used × the listed price; later runs reused saved answers, so the money actually spent was lower. The familywise claim covers the four primary pool means only.

03 / THE BENCHMARKS

The four benchmarks, and how to repeat this

Every case was turned into one multiple-choice question for Jev, so each answer is simply right (1) or wrong (0). The cards show exactly how. If your benchmark can be written the same way, you can evaluate it with CELEUS by following the five steps below.

Exact question sent to Jev

Data given

The task, its description, the tools, and every message of the run with its index.

Instruction

Judge ONLY the assistant message with zero-based message index i. Use the trajectory as evidence, including relevant tool results, but avoid hindsight from later success. An error propagates to causally dependent later actions until corrected or an independent subtask begins. A reasonable attempt facing an external failure is not automatically harmful. Do not penalize concurrent text and tool calls or the absence of written reasoning. A conversation-opening assistant greeting is acceptable progress only for the first message. Correctly following an explicit user request may count as progress even if it departs from the larger goal. An irrelevant mistaken statement with no downstream effect may be neutral rather than harmful.

Labels Jev chooses from

  • positive Correct, effective progress toward the user request or a valid correction.
  • neutral Reasonable exploration or repetition without meaningful progress or harm.
  • negative Incorrect, harmful, policy-violating, or causally dependent on an unresolved error.

Evaluate your own benchmark the same way

  1. Fix the pool first. Pin the dataset revision, write down the filtering rules (we dropped requests over 60 KB) and list every eligible case once, before asking the model anything. The result is about exactly this pool.
  2. One case, one multiple-choice question. Give the model the case as data plus a fixed set of labels. Score 1 if its label matches the reference label, otherwise 0. Settle any random choice (A/B order, which candidate to show) with a fixed seed in advance. If the model refuses a case, for example because it is too long, count it as wrong; never skip it.
  3. Choose the precision and confidence. We used ±2 percentage points, and 95% for all four benchmarks together, which means 98.75% for each one (the 5% error budget split four ways).
  4. Let CELEUS pick the cases. It asks 32 random cases first. After that, a cheap predictor built only from the case text (52 simple features such as length, digits and word overlap) points it to the most informative cases. The predictor never sees the answers and needs no extra LLM or GPU. Each case is asked at most once.
  5. Stop at the target. The interval is updated after every 10 answers and stays valid whenever you stop. Stop as soon as it is within ±2 points. Report the interval, the number of questions and the cost, and save every answer so a rerun never pays twice.
